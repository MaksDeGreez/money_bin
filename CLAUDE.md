# Money Bin

Master's capstone project (MSc Data Science, engineering project): a personal finance tracker for one person and an AI agent, local-first, running on the owner's machine. Receipt photo → OCR by the Python ML service → categorised items → ledger. A read-only REST API (`docs/openapi.yaml`) and a read-only MCP server at `/mcp` serve agents; writes come later. The history kept by the previous version of the app comes in through an importer (`docs/import-contract.md`). Current state: the planned features are built (the receipt flow from photo to ledger, local and hosted OCR, both categorisers, the read API and the MCP server, the dashboard, the evaluation harness); what is left is labelling receipts, the evaluation runs and fixes. The repository will be made public: nothing private may enter it.

## Domain

`docs/domain.md` is the reference: entities, invariants and the reasons behind them. Read it before touching models, migrations or anything that computes money. Money is always a decimal (`numeric` columns, `BigDecimal` in Ruby, decimal strings over HTTP), never a float.

`docs/decisions/` holds the architecture decision records, numbered (`0001-stack.md`: why Rails + PostgreSQL + Redis/Sidekiq + a separate FastAPI ML service, local-first; `0002-authentication-and-api-tokens.md`: sign-in, one user, Sidekiq Web protection, API tokens; `0003-agent-tooling.md`: sub-agents, skills, the Codex second-opinion review; `0004-receipt-ingest.md`: the receipt photo tool, its privacy rules and stable numbering; `0005-local-ocr-backend.md`: the local MLX OCR backend, its worker thread, shared prompt and post-processing; `0006-transaction-categoriser.md`: the transaction categoriser's model, baselines, time split, the selection-then-one-test-score protocol and limits; `0007-read-api.md`: the read API, query objects, cursor pagination, per-currency summaries, the OpenAPI version; `0008-mcp-server.md`: the MCP server, stateless, its token and Host/Origin rules, tools over the query objects; `0009-receipt-pages-photos-and-live-updates.md`: photos through an app controller, OCR requested once, live refreshes; `0010-receipt-ground-truth.md`: item ground truth from receipt files saved by hand, its own store, the tolerant XML reader, manual ground truth with categories, the pre-fill rule and the document schema versions; `0012-hosted-ocr-backend.md`: the OpenRouter OCR backend, zero data retention enforced per request, what is sent, cost per call; `0013-dashboard-charts.md`: the dashboard, Chartkick under the Content Security Policy, figures from the query objects; `0014-evaluation-harness.md`: the offline evaluation harness, item matching, model identity and the pre-fill rule, what `eval/results/` may hold; `0015-item-categoriser.md`: item category suggestions, the label memory, zero-shot over a closed label set, confidence from the model's own probabilities, one model for OCR and categorisation, what reaches a hosted model; `0016-decision-model-categoriser.md`: a hosted decision model (Jev) through OpenRouter's Decisions API as a categoriser, flat against two-stage, verification as a source of confidence, combining runs cross-validated by receipt, what is sent; `0017-ocr-batch-mode.md`: OCR in a provider batch as a separate retention opt-in, never a public photo URL, polling, the idempotency design, the repair-pass hand-over, what was verified live). Add a new numbered record for each infrastructure or process decision.

## Stack

- Ruby 4.0.10, Rails 8.1, PostgreSQL 18, Redis 8 (Homebrew on the owner's machine).
- Slim is the only template language (`config.generators` emits Slim). No ERB views.
- Tailwind CSS v4 via `tailwindcss-rails` (standalone CLI, no Node). Entry: `app/assets/tailwind/application.css`; the component classes (`btn-*`, `badge-*`, `callout-*`, `form-control`) are in `app/assets/tailwind/design-system.css`.
- Hotwire (Turbo + Stimulus) over importmap. No React/Vue/bundlers. Behaviour goes in `app/javascript/controllers/*_controller.js`.
- Receipt pages (`/receipts`, `ReceiptsController`): the list with its URL filter (`Receipt::Filter`) and `Pagination` (no gem), a receipt page with a photos column and a data column (partials `receipts/_photos`, `_data`, `_ocr_state`, `_details`, `_qr_comparison`, `_items`), the upload. OCR is queued only through `Receipts::RequestOcr` (once per receipt while `ocr_requested_at` is set; never a `reviewed` receipt); pages follow it live through `Receipts::LiveUpdate` (Turbo refresh broadcasts, called explicitly by the job and the services, never from model callbacks). Links to a receipt page carry `data-turbo-prefetch="false"`: opening an unread receipt queues OCR. Rules: `docs/domain.md`, "Receipt pages".
- Dashboard (`/`, `HomeController#show`): `Dashboard` (`app/models/dashboard.rb`: period `last12` or a year, currency UAH by default, `by` category or group, all in the URL; zero-filled months, the top ten categories then "Other", in BigDecimal) over `SpendingSummaryQuery`, `TopPayeesQuery` and `ReceiptCountsQuery`; partials `home/_headline`, `_months`, `_categories`, `_payees`, `_receipts`; `DashboardHelper` writes the money and the chart series. Charts are the `chartkick` gem (no groupdate): its inline scripts carry the CSP nonce, `config/initializers/chartkick.rb` replaces its `style=` container with the classes `chart chart-<sm|md|lg>`, Chart.js and Chartkick are pinned from the gem with `preload: false` and loaded only by `charts_controller.js`, and `app/javascript/charts.js` themes them from the design tokens (`--color-chart-1`/`-2`, redrawn on theme change) and shows the server's tooltip text. Rules: `docs/decisions/0013-dashboard-charts.md`.
- OCR batches (`/ocr-batches`, `OcrBatchesController`; rules: `docs/domain.md`, "OCR in a batch"): `OcrBatch` and `OcrBatchEntry` (a random `custom_id` per receipt, the only link to the provider's result), the hold `receipts.ocr_batch_id` (claimed under the row lock like `ocr_requested_at`: a held receipt is never queued one at a time, never in two batches, not pristine). "Read in a batch" on the list is a lazy Turbo Frame (`offer`) shown only when the service says batch mode is available (`OcrBatches::Availability`), with a confirmation (`new`: count, estimate, the wait, the retention). `OcrBatches::Create` splits a filter's receipts (100 and 150 MB per batch), `OcrBatchSubmitJob` sends them one at a time (`OcrBatches::Submit`: retry only when nothing can have been sent, split on too large, one oversized photo fails its receipt, `unknown` otherwise; every step under the batch lock while still `submitting`), `OcrBatchPollJob` (self-rescheduling, one chain by a cache token, advisory lock; restarted by `ensure_scheduled` from the pages and the worker's start) runs `OcrBatches::Check` (status, `OcrBatches::ApplyResults` entry by entry under row locks through `Receipts::ApplyOcr` then `ReceiptCategoriseJob`, the repair-pass hand-over to `RequestOcr` up to max(5, 10%), follow-ups marked per entry (`followed_up_at`) and finished only when `settled?`, release on failure or expiry, after five days unfollowable, or by the owner ("Release the receipts"), deletion upstream at once). "Enter by hand" clears the hold and wins. The list filters by `ocr_batch`.
- The review form (`receipts/_review`, `_item_row`, `_qr_hint`, `_duplicates`) replaces the read-only data column while a receipt is reviewable (`Receipt#reviewable?`); `PATCH /receipts/:id` saves it through `Receipts::Review` (`intent=accept` saves and books with `Receipts::Accept` in one database transaction), `POST /receipts/:id/enter_by_hand` is `Receipts::EnterByHand`, `POST /receipts/:id/suggest_categories` queues `ReceiptCategoriseJob` ("Suggest categories again", `receipts/_suggestions_state`, outside the form). Receipts have a `lock_version` the form carries: a stale form saves nothing and keeps the typed values. `intent=ground_truth` ("Save as ground truth", Ctrl/Cmd+Shift+S) saves and snapshots the receipt as its `manual` `ReceiptGroundTruth` through `Receipts::SaveGroundTruth` (never books; replacing asks first with a diff); `prefilled_by` comes from `ReceiptGroundTruth::Prefill` (`ocr_model_name` + `ocr_prompt_version`, `filled_from`, `categoriser_model_name`). The ground truth shows under the data column (`receipts/_ground_truth`, `_ground_truth_check`); a tax-service record is checked through `Receipts::GroundTruthChecksController`. The list filters by ground truth (`truth`, `check`) and "Next receipt to label" follows `Receipt::Filter#next_to_label`. Money typed in a form goes through `MoneyInput` (a comma is a decimal separator, never rounded). Lines per category come from `CategoryLines`, shared by acceptance and manual entry (`ManualExpense`, `/transactions/new`); `/transactions/:id` shows one transaction (`TransactionsController`; the list is below). Stimulus: `form_guard_controller.js` (unsaved changes pause live refreshes, guard leaving, Ctrl/Cmd+S, +Shift+S and +Enter), `line_items_controller.js`, `combobox_controller.js`, `money_totals_controller.js` (BigInt hundredths), `receipt_review_controller.js` (also "Fill the form from the tax-service record"), `autofocus_controller.js`. Rules: `docs/domain.md`, "Review", "Manual entry" and "Manual ground truth".
- Category suggestions (`docs/domain.md`, "Category suggestions"): `Receipts::SuggestCategories` fills `suggested_category`, `confidence` and `suggested_by` (`memory` or `model`) on the items of an `extracted` receipt and records `categoriser_model_name` (the model; `label-memory` when only the memory suggested), `categorised_at` and `categoriser_error`. The label memory (`LabelMemory` in `app/queries/`, names matched by `ItemName.key`, stored as `receipt_items.name_key`; the Python twin `ml/evaluation/label_memory.py` reads the same cases in `ml/tests/fixtures/item_name_keys.json`) goes first, the rest go to `MlClient#categorise` in one call with `Categories::ItemCandidates` (every category but Uncategorised and Adjustments). It never writes `category_id` or `accepted_by_user`, never moves `lock_version`, never fails the receipt. `ReceiptOcrJob` runs it after `ApplyOcr`; `ReceiptCategoriseJob` (queue `receipt_categorise`, worked first by the OCR capsule) on request. A card slip's own suggestion is `Receipts::SuggestSlipCategory`'s (`docs/domain.md`, "Card slip suggestions"): the payee the merchant matches and its booked history first (`PayeeHistory`, `categoriser_model_name` `payee-history`), else `MlClient#categorise_transactions`; the same jobs call it for a slip, and a review save that turns a receipt into a slip queues it.
- Transactions list and suggestions (`/transactions`, `docs/domain.md`, "Transaction suggestions"): `TransactionsController#index` over `Transaction::Filter` (URL state) and `TransactionsQuery` (also `payee`, `uncategorised`, `currency`), `Pagination`; partials `transactions/_filter`, `_suggestions_panel`, `_transaction` (a tbody per transaction), `_review_line`; `review_queue_controller.js` (j/k/t/c). Uncategorised lines (no category or Uncategorised: `TransactionLine.uncategorised`) carry the stored suggestion (`suggested_category_id`, `suggestion_probability`, runner-up, `suggestion_source`, `suggestion_model_version`), filled by `Transactions::SuggestCategories` (`TransactionSuggestionsJob`, `TransactionSuggestionRun`; batches of 200 to `MlClient#categorise_transactions` with `Categories::TransactionCandidates`; `update_all` on the suggestion columns only). `POST /transactions/:id/categorise` is `Transactions::Categorise` (only uncategorised lines, row lock + `lock_version`, `Transaction#status_after_categorising`, `category_origin` `person`/`suggestion`/`bulk` with the taken probability and artefact). The bulk action is `BulkAcceptance` (a preview snapshot of items, confirmed once) and `BulkAcceptanceJob` (`BulkAcceptanceItem#apply!`, each item once; stale and changed rows skipped and counted); `Transactions::BulkAcceptancesController`, `Transactions::SuggestionRunsController`.
- Sidekiq is the Active Job adapter (`config/sidekiq.yml`); Redis is also the cache store and the Action Cable adapter. No Solid Queue/Cache/Cable. `ReceiptOcrJob` has its own queue (`receipt_ocr`) in a Sidekiq capsule with one thread: the local OCR model reads one receipt at a time. All capsules' threads together stay within the database pool (`test/config/sidekiq_config_test.rb`).
- Active Storage on the local disk (`storage/`, git-ignored). Receipt photos never leave the machine unless the owner turns on a hosted OCR backend. Rails' own Active Storage routes are not drawn (`config.active_storage.draw_routes = false`): they skip sign-in. Uploading or showing a photo goes through an app controller behind the `Authentication` concern, never `url_for(blob)` or `rails_blob_path`: `Receipts::PhotosController` (`receipt_photo_path(receipt, attachment, :thumb | :page | :full)`) serves a receipt's photos and their JPEG variants (`Receipt` named variants, made once and kept).
- The ML service: `ml/`, Python 3.12, FastAPI, managed with `uv`. Endpoints `/health`, `/ocr` (1-3 images → receipt with items), `/categorise` (one receipt's item texts, the candidate categories the request carries, an optional merchant → 1-3 candidates per item with scores, `score_kind`, `calibrated`, `prompt_version`), `GET`/`POST /categorise/transaction` (the transaction categoriser, `ml/app/transactions.py`: 1-500 transactions and the app's category list → 3 candidates each with probabilities and `source` model/mix/history; the artefact from `TRANSACTION_CATEGORISER_MODEL` or the newest `*.serving.joblib` in `~/Documents/money_bin_data/models/`, loaded lazily with its sentence encoder, 501 without one; always local, no backend setting; classes matched to the listed categories by group and name, 422 `categories_mismatch` otherwise). The OCR backend is chosen by `OCR_BACKEND`, the categoriser apart by `CATEGORISE_BACKEND` (`stub`, `mlx`, `openrouter`, `decisions`, or `off`, which the Rails app reads too (`ItemSuggestions`): no suggestion at all, label memory included, for labelling receipts no categoriser pre-filled; `ml/app/categorise/`, the narrow `Categoriser` interface in `base.py`, the category hand-over in `taxonomy.py`, shared prompt in `prompt.py`); with both on `mlx` they share the one worker thread and, when `MLX_CATEGORISE_MODEL` is empty, the one model. OCR backends: `stub` (default, invented data in the final shapes), `mlx` (a local Qwen VL model through mlx-vlm on Apple silicon: one worker thread owns the model, constrained JSON decoding, `MLX_OCR_*` settings) and `openrouter` (a hosted vision model through OpenRouter: every request limited by code to the model's zero-data-retention endpoints without Safety Retention, read from OpenRouter's public endpoint list, plus `zdr: true` and `data_collection: "deny"`, none of it configurable; sends only the re-encoded photos and the fixed prompt, no attribution headers; `OPENROUTER_API_KEY`, `OPENROUTER_OCR_MODEL` with no default, other `OPENROUTER_*` settings; records cost, latency and provider per call). Batch mode (`ml/app/batch/`, `/ocr/batches`: capability, estimate, create, status, results, delete; `openrouter` only, others 501) reads many receipts in one OpenRouter batch at about half the price: NOT zero-retention (kept until deleted, at most 30 days), so off unless `OPENROUTER_BATCH_ALLOW_RETENTION=true` (no synchronous setting reaches it), routed with `provider.only` = `OPENROUTER_BATCH_PROVIDERS` and no fallbacks, model `OPENROUTER_BATCH_MODEL` (a `:batch` variant), the same request body and answer reading as `/ocr` (no repair pass: `ocr_parse_failed` with `retry_sync`), photos only inline (never a URL; refused inline images fail the batch), the caller's random keys as `custom_id`, no state kept. The local categoriser scores every candidate slug over a token trie (the model's own probability, renormalised over the list); the hosted one (`OPENROUTER_CATEGORISE_MODEL`, the same `OpenRouterClient` and zero-retention rules) gets the item names only, never the merchant, amounts, dates or ids, and scores from token log-probabilities when the endpoint returns them, else a fixed 0.5 marked `fixed`. `decisions` (`app/categorise/decisions.py` over the Decisions API client `app/decisions.py`, through the same `OpenRouterClient` with `decisions=True`; `DECISIONS_MODEL` with no default, e.g. `typesafe/jev-1.14`, never a `~...-latest` alias; `DECISIONS_STRATEGY` `flat` (default) or `two-stage`, `DECISIONS_RECEIPT_CONTEXT`, `DECISIONS_MAX_QUESTIONS`) asks one typed `choice` question per item and takes the model's probability for every category (`score_kind: decision_probability`); the request body is `model`, `state` (item names, optionally labelled example names), `questions` (fixed instructions, category names and descriptions) and `provider`, nothing else; every answer is checked against its question, a refusal fails the receipt (422). Its `verify` (offline only for now) asks a yes/no question per candidate of another run. Never use the Decisions client for transactions, payees or bank descriptions. `CATEGORISE_CALIBRATION_FILE` (isotonic, fitted by `python -m evaluation.item_categories_calibrate`, outside git) turns raw scores into measured precision. Receipt photos leave the machine only with OCR on `openrouter`, item names only with categorisation on `openrouter` or `decisions`; ledger data never does, and the transaction categoriser stays local. The prompt, the parsing with one repair pass and the post-processing (plain code, never rounds money) are shared in `ml/app/ocr/`. mlx-vlm is pinned in the `mlx` dependency group, which installs only on macOS arm64. `ml/evaluation/` runs a backend over the receipt set (`python -m evaluation.ocr_run`, output outside git; a hosted run also records cost per receipt) and scores it against the QR codes (`python -m evaluation.ocr_fields`, with seconds and cost per receipt); `python -m evaluation.item_categories_run` runs a categoriser (and with `--memory` the label memory, earlier receipts only) over the labelled items of the ground-truth export with the categories from `bin/rails "categories:export_items[FILE]"`, and `python -m evaluation.item_sanity` smoke-tests one on the invented sanity set (98 items; reliability, auto-accept share at 95% precision, cost); with `--backend decisions` both take `--strategy`, `--no-receipt-context`, `--max-questions`, and the runner `--examples K` (similar items labelled in earlier receipts, `LabelMemory.similar`) and `--verify RUN_DIR`. `python -m evaluation.item_categories_combine` combines runs (`cascade`, `average`, `learned`: logistic regression cross-validated by receipt and forward in time, each block of receipts scored by a fit on earlier ones only) into a run folder of the same format, leaving out labels a combined categoriser pre-filled (every run's `run.json` names the categorisers behind it where the harness reads them: `model_name`, `memory`, and `combined_from` for the label memory that supplied examples and a verified run's categorisers), and reports how often the runs agree and how precise agreement is. `ml/README.md` is the contract.
- Minitest + fixtures, WebMock (no test reaches the network), SimpleCov. No RSpec, no FactoryBot, no system tests. Python: pytest, ruff.
- Authentication: the Rails 8 generator's code (`Authentication` concern, `Session`, `Current`), bcrypt. Exactly one `User`, created on the command line; no sign-up, no e-mailed password reset. Every page needs a signed-in session unless the controller calls `allow_unauthenticated_access`. The cookies are `money_bin_v2_session_id` (sign-in, `Session::COOKIE_NAME`) and `_money_bin_v2_session` (Rails session), not the defaults another local app would share; sign-in and sign-out reset the Rails session. Sidekiq Web (`/sidekiq`) sits behind a route constraint on the session cookie (a 404 otherwise).
- API: personal API tokens (`ApiToken`: `mbt_` prefix, SHA-256 digest stored, scopes `read` / `read_write`, revoked never deleted). API controllers live in `app/controllers/api/v1/` and inherit from `Api::BaseController` (`ActionController::API`, `Authorization: Bearer` only, errors `{"error": {"code", "message"}}`; an unknown, malformed or dangling query parameter is a 422 `invalid_parameter`, never ignored). Browser cookies never authenticate the API. The read endpoints (`transactions`, `accounts`, `categories`, `summary`, `receipts`) keep their reading logic in query objects in `app/queries/` (plain Ruby, no HTTP; the MCP tools call them too) and render through the plain JSON builders in `app/serializers/` (money and quantities as decimal strings via `JsonFormat`). Lists use keyset pagination (`KeysetCursor`, `limit` 50 by default, 200 at most, an opaque `cursor`). `docs/openapi.yaml` (OpenAPI 3.0.3: committee does not validate 3.1) describes every endpoint; change it in the same change as an endpoint. Summaries count booked transactions only, leave transfer legs out, split by lines and never add two currencies together.
- MCP server: `/mcp` (`McpController`, `McpServer`, tools in `app/mcp/mcp_tools/`), the official `mcp` gem, Streamable HTTP, stateless (no session, one JSON answer per POST; other methods 405), tools only. The same personal API tokens and checks as the API (`ApiTokenAuthentication`; either scope, every tool only reads); before that, the Host must be localhost/127.0.0.1/::1 (or `APP_HOST`) and a browser `Origin` must be the app's own (403 otherwise). Each tool is a thin adapter over a query object: arguments checked by its JSON Schema and then `QueryArguments` (shared with `Api::QueryParameters`), a bad one is a tool error (`isError`) naming it; the result is a short text plus `structuredContent` equal to the REST endpoint's JSON, with an `outputSchema` generated from `docs/openapi.yaml`; annotations read-only, idempotent, closed-world; the receipt tools' text names a card slip's category or suggestion (`ReceiptSerializer#common` carries it, null on other receipts). No write tools, no photos. Claude Desktop connects through `mcp-remote` (README).
- Times are shown in Kyiv time (`config.time_zone = "Europe/Kyiv"`); the database stores UTC.
- `dotenv` loads `.env*` in development and production (`.env.example` lists the settings). The ML service reads only its environment: `bin/dev` hands it `.env` (`Procfile.dev`, `uv run --env-file ../.env`; the shell wins over the file), a command run by hand passes the file itself, and `GET /health` says which backends are running. Test runs read no `.env` file (`config/application.rb`); only real environment variables reach them.

## Running it

- `bin/setup` — gems, `uv sync` in `ml/`, `.env` from `.env.example`, `git config core.hooksPath .githooks`, services, `db:prepare`, then `bin/dev` (`--skip-server` to stop before it). `bin/worktree-setup` does the same in a linked git worktree and links `.env`, `.env.local` and `config/master.key` from the main checkout. `bin/worktree-remove PATH` retires a clean worktree: drops its test databases, removes it, prunes (freeing its test Redis database) and deletes the local branch when GitHub shows its pull request merged.
- `bin/rails "import:money_bin[DIR]"` — imports an export of the previous app from the folder DIR (kept outside the repository); `DRY_RUN=1` does everything, prints the counts and rolls back. All or nothing; a second run of the same export writes nothing and keeps edits made in the app, while a row that changed in the export overwrites that row (`import_digest`). Prints counts and warnings only. Contract and rules: `docs/import-contract.md`; code: `app/services/legacy_import/`; fixture: `test/fixtures/files/legacy_export/` (re-hash it with `test/support/legacy_export_files.rb` after a change).
- `bin/rails user:create` — creates the one user (asks, or reads `MONEY_BIN_EMAIL` / `MONEY_BIN_PASSWORD`); `bin/rails user:password` sets a new password and ends every browser session. Logic in `Users::CommandLine`. Never print or log a password or a plain token.
- `bin/dev` — Puma on port 3100, Sidekiq, the Tailwind watcher and the ML service on 127.0.0.1:8100 (`Procfile.dev`, foreman). Wipes compiled assets first. Skips the ML service when `uv` is missing.
- `bin/db-backup [--verify] [DIR]` — `pg_dump` of the development database (or `DATABASE_URL`) to `~/Documents/money_bin_data/backups/<database>-<UTC time>.dump`, mode 0600; `--verify` restores it into a throwaway database and compares every table's row count. Refuses a folder inside a git repository. The database only, not `storage/`. Run it before anything that rewrites the ledger (an import, a receipt load, a migration with data in it).
- `bin/services` — checks PostgreSQL and Redis and starts a stopped one with `brew services` (`--check` only reports).
- `bin/ci --summary` — the full check suite, one line per step plus the output of failed steps (full log in `tmp/ci/last.log`): setup, RuboCop, slim-lint, bundler-audit, importmap audit, Brakeman, the leak check of the tracked files, Tailwind build, Rails tests, seeds, then ruff check, ruff format and pytest for `ml/` and again for `tools/receipt_ingest/`. Run it before every push. GitHub CI is the merge gate.
- `bin/rails test path/to/test.rb[:LINE]` for targeted tests. Only a full `bin/rails test` checks the 80% line coverage minimum (`test/support/coverage.rb`). In `ml/`: `uv run pytest` (70% minimum), `uv run ruff check .`, `uv run ruff format --check .`.
- `bin/pr-wait <n>` — waits for a pull request's checks and prints one final line (`GREEN`, `FAILED check=<job>`, `CONFLICT`, ...); run it as a background command.
- `bin/leak-check --tree` / `--history` — looks for the forbidden terms of `~/Documents/money_bin_data/leak_terms.txt` (outside the repository) in the working tree / in every local commit; the pre-push hook runs `--pre-push`. Prints where, never the term.
- `bin/codex-review` — a second-opinion review of a diff or a plan by the OpenAI Codex CLI, read-only (`codex-review` skill, `docs/decisions/0003-agent-tooling.md`); run it as a background command. It runs on `gpt-6.2-sol` with `high` reasoning effort unless `--model` / `--effort` (or `CODEX_REVIEW_MODEL` / `CODEX_REVIEW_EFFORT`) say otherwise. Codex cannot reach the database: `--sql FILE` runs your read-only queries first and hands it the results. The prompt goes to a hosted model, so those queries return counts, sums and ids, never personal detail.
- `bin/rails "receipts:load[DIR]"` — loads the receipt ingest tool's output folder DIR (`~/Documents/money_bin_data/receipts/`) as `Receipt` rows with their photos; `DRY_RUN=1` checks everything, prints the counts, uploads nothing and rolls back. Verifies the whole `receipts.jsonl` and every image first; then one database transaction per receipt (not all or nothing). A second run of the same folder writes nothing. Sets the QR ground truth (`qr_*`), `ingest_id` and `batch`, never `kind` or anything OCR owns; enqueues no OCR. Prints counts (per batch folder name too) and receipt ids only. Code: `app/services/receipt_load/`; rules: `docs/domain.md`, "Receipt load"; tests build a synthetic folder (`test/support/receipt_ingest_folder.rb`).
- `bin/rails "receipts:import_ground_truth_xml[DIR]"` — imports item-level ground truth from receipt files the owner saved by hand from the tax service's receipt page, `rcpt_NNNNNN.xml` in DIR (`~/Documents/money_bin_data/dps_xml/`, outside git, read only, nothing written there); `DRY_RUN=1` rolls back. **No code in this repository requests anything from the tax service, ever** (no client, token, setting or test fetch; `docs/decisions/0010-receipt-ground-truth.md`); the input is local files only, and real files never enter git (tests write invented XML: `test/support/dps_xml_files.rb`). Each file is read by `DpsXml::Reader` (a size limit, no DOCTYPE/entities, strict parse; one class per format variant, `DpsXml::Check01` is from documentation and unconfirmed), cross-checked against the receipt's `qr_*` (a disagreement is not imported; a file is verified only by the receipt number or the total and time, never the register number alone; an unverified file is imported with its status in the export), and stored as the receipt's `dps_xml` `ReceiptGroundTruth`; same digest = unchanged, a changed file replaces it unless a person checked it (conflict). Never writes the receipt, its items, a transaction, OCR or QR columns. One database transaction per file; prints counts and receipt ids only. `bin/rails "receipts:export_ground_truth[OUT_DIR]"` writes `ground_truth.jsonl` for `ml/evaluation/` (every record as document schema version 2: `category_slug` per item and for a slip, `categories_known`, `prefilled_by`, `categories_prefilled_by`; version 1 records stay stored as they are; refuses a folder inside git, mode 0600; `qr_check` repeats the cross-check). A receipt with ground truth is not `pristine?`, so the receipt load keeps it. Rules: `docs/domain.md`, "Receipt ground truth".
- `make eval` (root `Makefile`; `make eval-check` validates and writes nothing) — the evaluation harness (`ml/evaluation/harness.py`): reads the receipt set, every run folder under `RUNS_DIR` (OCR runs and item-category runs, `run.json` + `predictions.jsonl`, `task` missing = `ocr`) and the ground-truth export (`RECEIPTS_DIR`, `RUNS_DIR`, `GROUND_TRUTH_DIR`, defaults under `~/Documents/money_bin_data/`), never the database, and writes aggregate JSON per run and per comparison, `index.json` and Markdown/CSV tables to `eval/results/`, byte-identical for the same inputs. Item matching is one-to-one (Hungarian, one assignment per variant `main`, `strict`, `lenient`, name similarity + amount); a `dps_xml` record the QR contradicts and a record checked as `differs` are left out; `dps_xml` before `manual`; a record pre-filled by the model a run evaluates (`prefilled_by`, `categories_prefilled_by`) is left out of that run and counted; "the same model" is decided in `ml/evaluation/models.py` only (same base model whatever quantisation, host or dated slug; another size, version or tier is another model, but only with proof: anything unexplained, a local folder, `source:unknown-model` leaves the record out; a combined item-category run counts as every categoriser in its `combined_from`). Item-category runs also report calibration (reliability bins, ECE, Brier) and split by an open set of `source` values. **`eval/results/` holds numbers, category slugs, model names and run parameters only**: never an item name, a merchant, a receipt id, a single receipt's amount or date, or a local path. Only `evaluation/results.py`'s writer writes there, and it refuses anything outside its declared structure; per-receipt detail goes to `--diagnostics DIR` outside git. Definitions: `ml/README.md`, "The evaluation harness"; reasons: `docs/decisions/0014-evaluation-harness.md`.
- `uv run --project tools/receipt_ingest receipt-ingest RAW_DIR OUT_DIR` — the receipt ingest tool (`tools/receipt_ingest/`, Python 3.12, uv, its own `pyproject.toml`, lock and README; not part of the app or of `ml/`). It turns the owner's receipt photos in `~/Documents/money_bin_receipts/raw/<batch>/` (read-only, never modified) into a numbered set in `~/Documents/money_bin_data/receipts/`: `images/rcpt_NNNNNN_K.jpg` with all metadata stripped, crops, `receipts.jsonl` with the QR ground truth, `groups_review.html`, `state.json` (what keeps the numbers stable), and the owner's `groups_override.yaml`. Photos, EXIF values and QR payloads are personal data: the tool prints counts only and refuses an output folder inside a git repository; keep its tests synthetic and commit no image. Checks in that folder: `uv run pytest` (80% minimum), `uv run ruff check .`, `uv run ruff format --check .`. Reasons: `docs/decisions/0004-receipt-ingest.md`.
- `cd ml && uv run python -m categoriser.selection EXPORT_DIR [--out DIR] [--encoders e5-base e5-large]`, then `uv run python -m categoriser.score EXPORT_DIR --selection FILE` — the transaction categoriser (`ml/categoriser/`). The rows: one per non-transfer transaction (largest line labels a split; rows without a category, unmapped, outside `db/seeds/taxonomy.yml` or Uncategorised dropped), split by date into fitting rows, a validation slice (the end of the training period) and the last 20% as the test set. `selection` fits every candidate (TF-IDF + logistic regression, which is the first version; local sentence embeddings; recency and class weights; a hybrid with the payee's and MCC's history) on the fitting rows, tunes and compares them on the validation slice only, and picks one by a rule fixed in advance; the test set is sealed (`SealedTest` refuses) and the selection JSON holds no test metric. `score` is the only step that unseals it: it refits the chosen configuration on training + validation and scores it, the first version and the rule baselines once (bootstrap intervals by rows and by days, McNemar, segments), checks that the export, split, encoders and committed code match the selection's, appends each unsealing to `~/Documents/money_bin_data/categoriser-test-scores.jsonl` before reading a test row, and refuses a second score of the same export without `--rescore-reason`. Writes the model file (it holds payee names) and the JSON files (category names and numbers only) to `~/Documents/money_bin_data/models/`, the embedding cache to `~/Documents/money_bin_data/cache/embeddings/`, and refuses folders inside a git repository; prints aggregates only. Runs locally only (the encoders load from the local Hugging Face cache; torch and transformers are in the `embeddings` dependency group, Apple silicon only, and the tests use a fake encoder); never send transaction data to a hosted model. Reasons and the protocol: `docs/decisions/0006-transaction-categoriser.md`. Then `uv run python -m categoriser.serving EXPORT_DIR --selection FILE` fits the chosen configuration on every labelled row (test period included; no metric, the evaluated numbers stay the scored fit's) into `<stamp>.serving.joblib` + `.serving.json` in the same folder, refusing another export, taxonomy, split, encoder, an unscored selection or changed `ml/categoriser/` code; `ServingModel` scores through the training code's `System` (a test checks serving = training).
- `bin/favicon` — regenerates the favicon set in `public/` (`favicon.ico`, `favicon-96.png`, `apple-touch-icon.png`) from `design/favicon/source.png`. The header logo (`app/assets/images/logo.png`, 160 px) is a one-off `sips` resize of the same file. There is no web manifest.

Databases: `money_bin_v2_development`, `money_bin_v2_production`, and for tests `money_bin_v2_test` in the main checkout or `money_bin_v2_test_<worktree>` in a linked worktree (`config/worktree_isolation.rb`). Redis databases: 4 production, 5 development, 6 tests in the main checkout, one of 7..15 for tests in a worktree (`config/redis_url.rb`). Another local app on the same Redis uses 0, 1 and 2, and its git worktrees take test databases from 3 upward, lowest free first; the two apps can only meet when that app has several worktrees running tests at once, a known and accepted limit (it is no longer developed). The way out, if it ever matters, is `REDIS_URL` pointing at another Redis instance. The names, numbers and ports are chosen not to clash with that app. `DATABASE_URL` and `REDIS_URL` override them (CI uses both).

## Working with the owner

- For non-trivial work: research, write a plan with recommended defaults, put the open decisions to the owner as short questions (at most four at a time, recommended option first), and wait for approval before implementing.
- Commit, push or open a pull request only when the owner asks. When they ask for a PR they expect the whole run: the `ship` skill (`.claude/skills/ship/`) is that pipeline.
- Every change goes through a branch and a pull request. Never push to `main` (the pre-push hook refuses it; `ALLOW_PUSH_TO_MAIN` is the owner's emergency switch, never an agent's). Pull requests are squash-merged once the `CI` check is green; squash is the only merge method and `--admin` is never used.
- Small commits with plain messages. Commit messages and pull requests never carry AI attribution of any kind: no co-author trailers, no "generated with" footers.
- Do not end a turn to wait for CI. Start `bin/pr-wait` as a background command and carry on with whatever does not depend on it.
- Keep changes you did not make: other sessions and agents may be working in the same tree. Do not revert unrelated work.
- Sub-agents: the `implementer` agent (`.claude/agents/implementer.md`) for sizeable implementation, the `reviewer` agent (`.claude/agents/reviewer.md`, read-only) on every non-trivial diff before the PR and on plans, plus `bin/codex-review` for changes to the data model, a migration, money arithmetic or an importer. Brief them with the goal, the scope and what the owner has already decided; give the reviewer the code, not your conclusion; trace every review finding in the code before acting on it. Independent streams of work each get their own worktree (`bin/worktree-setup`).
- The previous version of the app, kept outside this repository, is a read-only reference for conventions: never write to it, never run its scripts, never connect to its databases, and copy no data or personal detail from it.
- The shell is zsh on macOS: quote globs, there is no `timeout` command.

## Conventions

- Keep `README.md`, this file and `docs/` current in the same change: `docs/domain.md` for the model and its reasoning, `docs/decisions/` for infrastructure and process decisions.
- No secrets and no personal data in git: not in code, fixtures, docs, commit messages or branch names. Fixtures and examples are synthetic. Secrets live in `.env` (git-ignored); private files live outside the repository. `.githooks/pre-commit` (gitleaks) and `.githooks/pre-push` (leak check) back this up, and CI scans the history with gitleaks.
- Tests: controller tests sign in with `sign_in_as users(:owner)` (`test/support/session_test_helper.rb`); API tests send `bearer(plain_token(:agent_read))` (`test/support/api_token_test_helper.rb`; fixtures store only digests), include `OpenapiTestHelper` and `ApiRequestTestHelper`, and check every response against `docs/openapi.yaml` (`assert_api_conform(status)`, or `assert_api_response_conform(status)` for a request that is wrong on purpose). Every object schema there has `additionalProperties: false` and lists all its properties in `required`; a new documented path or status needs an example in `test/integration/api_contract_test.rb`, which fails otherwise. The suite checks that every fixture is valid (`test/models/fixtures_test.rb`): add new models there. MCP tests (`McpTestHelper`: `host! McpTestHelper::HOST`, `mcp_call_tool`, `mcp_structured`) speak JSON-RPC to `/mcp`; a new tool needs its entry in `TOOL_EXAMPLES` of `test/integration/mcp_server_test.rb` (a call, a bad argument, its REST twin), which fails otherwise.
- CI never needs model weights, receipt images or personal data. Tests stub HTTP with WebMock; the ML tests use the stub backend.
- Views: Slim only. Use the UI helpers before writing markup: `ui_button`, `ui_link_button`, `ui_button_to` (variants `primary`, `secondary`, `ghost`, `soft`, `danger`, `link`; sizes `sm`, `md`, `lg`, `icon`), `ui_badge` (tones `neutral`, `accent`, `signal`, `muted`, `solid`, `danger`), `ui_icon` (Lucide), `ui_kbd` (key caps), `ui_classes` (merges Tailwind classes), the partials `ui/page_header`, `ui/callout` (also `hidden:`, `data:`), `ui/flash`, `ui/theme_toggle`, `ui/pagination`, `ui/count_tabs`, `ui/totals_footer`, the component classes `filter-bar`, `photo-thumb`, `photo-frame`, `review-layout` / `review-photos` (a sticky photo column next to a form), `line-editor` / `line-row-receipt` / `line-row-simple` (editable rows), `combobox`, and `UiFormBuilder` (the default form builder: `f.text_field` and friends, `f.money_field` (decimal text, typed value kept), `f.category_select` (type-to-filter combobox over a hidden grouped select), `f.file_field`, `f.select`, `f.check_box`, `f.radio_button`, `f.submit`, `f.hint`, `f.error_for`). In Slim, a `data=` hash keeps underscores (`data-form_guard_target`): pass data attributes through Rails helpers (`tag.div data: {...}`, `form_with data:`), not Slim attribute hashes. Prefer adding a helper or partial over a one-off; the `design-system` skill (`.claude/skills/design-system/`) is the way to add a primitive, change colours or fonts, or audit views that bypass the system.
- Charts: a Chartkick helper in a view with an `id`, `discrete: true` and a height `sm`/`md`/`lg` (never a style), inside an element with `data-controller="charts"`; its data from a query object through `DashboardHelper#dashboard_series` (money as exact decimal strings, a Float is refused, the tooltip text per point formatted on the server); the same figures as a table in a `details.chart-figures` beside it; an empty state instead of an empty chart. No aggregation in views or controllers, and never the CSP loosened for a chart.
- Tailwind utilities must appear literally in `app/views`, `app/helpers`, `app/form_builders` or `app/javascript`; never build `"bg-#{tone}"`. Utilities with `:`, `/`, `[` or `]` go in `class="…"` in Slim, not in dot shorthand. No inline JS of our own: the exceptions are the theme boot script in `app/views/layouts/_head.html.slim` and the one script per chart that the Chartkick helper writes, both with the CSP nonce. The Content Security Policy (`config/initializers/content_security_policy.rb`) blocks any inline script or style without the nonce, `on…=` attributes included, and allows only this app plus the Google Fonts hosts.
- `.rubocop.yml` (rails-omakase, also lints the Ruby scripts in `bin/`), `.slim-lint.yml` and ruff (`ml/pyproject.toml`) are the style authorities; `bin/ci` runs all three.
- Dates and times are shown in Kyiv time through `config.time_zone`; nothing converts time zones by hand.
- The ML service's contract is `ml/README.md`: money and quantities are decimal strings, every error has the shape `{"error": {"code", "message"}}`. A new OCR backend is a class in `ml/app/backends/` registered in `BACKENDS`, a new categoriser one in `ml/app/categorise/` registered in `CATEGORISERS`; neither commits keys or weights.
